# 架构说明

## 1. 定位与边界

输入：告警源（Nightingale）的 HTTP 回调事件。
输出：聚合后的工单、模型诊断结论、飞书通知、只读 Web 页面。

不做的事：不执行任何变更（不重启、不登录、不改配置）；对 Kubernetes 只读；
不接管告警源自身的通知与规则。

## 2. 进程与并发模型

单副本进程，FastAPI + 后台线程：

```
HTTP 请求线程           后台单线程 worker              定时巡检线程（30s）
接收事件                 采集 + 诊断 + 推卡             过期、探测、汇总、清理
   │                        │                              │
   └──────────── 状态都在 SQLite，进程内锁串行化写 ─────────┘
```

两条硬约束：

1. **锁只包数据库的读-判-写**。Prometheus、Kubernetes、模型、飞书都是网络调用，一律不持锁。
   否则长事务会阻塞接收端的写入。
2. **接收端只做入库与关联，副作用出锁**。采集、诊断、推送落库为「待执行」状态，由 worker 消费。
   接收接口从十几秒降到百毫秒级。

## 3. 数据模型

| 表 | 粒度 | 关键约束 |
| --- | --- | --- |
| `raw_events` | 单次请求 | `event_id` 唯一；原文同时按天写入 `data/raw_events/*.jsonl` |
| `alerts` | 一条告警 | `fingerprint` 上的部分唯一索引保证同一告警在 FIRING 期间只有一行 |
| `incidents` | 一个工单 | `incident_id` 唯一；`alert_count` 由关联表重算 |
| `incident_alerts` | 关联关系 | `(incident_id, alert_id)` 唯一，记录关联类型（根因/关联/复发） |
| `incident_events` | 时间线 | 追加写，工单的全部状态变化与推送记录 |
| `feishu_messages` | 推送留档 | 幂等依据：同一目标同一类型只成功推送一次 |
| `llm_calls` | 模型调用 | 保存 prompt 与响应，便于复盘判断依据 |
| `resource_relations` | 拓扑 | 实体间的显式关系，供关联与影响面计算 |

不变量：**告警幂等键**为「源 `hash` + `status` + `trigger_time`」；
**去重的硬保证**是数据库唯一索引，应用层的先查后建只是快路径。

## 4. 状态机

**Alert**：`FIRING` → `RESOLVED`。结束原因 `resolved`（告警源显式恢复）或 `stale`（超过过期窗口无事件）。

**Incident**：

```
        ┌──────────── 新告警挂入 / 同指纹复发 ────────────┐
        ▼                                                │
     OPEN ──认领──▶ ACKNOWLEDGED ──全部告警恢复──▶ RECOVERING ──校验通过──▶ RESOLVED
        │                                                │
        └────────────── 与其它工单同源 ──▶ MERGED ◀──────┘
```

- 只有两个来源能让工单进入 `RECOVERING` 并最终关闭：告警源的显式恢复信号，或主动探测拿到权威判据。
  告警静默本身不作为恢复依据。
- `RESOLVED` 的工单在复发窗口内可以被同指纹告警重新打开，并保留原时间线。

## 5. 关联算法

按顺序短路：

1. `force_link`：规则表里显式声明的强关联。
2. `causal_rule`：因果规则命中（例如同一节点的多个衍生故障）。
3. `never_link`：显式排除，优先级最高。
4. 拓扑距离 ≤ 2 且评分超过阈值（同实体、同节点、同集群、时间接近等维度加权）。
5. 都不命中时，按指纹查找复发窗口内未合并的工单，命中则挂回原单；仍未命中才新建工单。

规则与阈值放在 `rules/correlation.yaml`，`POST /api/v1/rules/reload` 热加载。

## 6. 诊断链

```
上下文采集（Prometheus 回溯 + K8s 事实 + 拓扑 + 告警列表 + 影响面）
      ↓
模型调用（单轮、无工具、JSON 输出；出网前脱敏，返回后还原）
      ↓
结构化校验：必填字段齐备、置信度夹取到 0..1、证据为空时置信度压到阈值以下并标注证据缺口
      ↓
落库（结论、置信度、完整输出）+ 时间线记录引擎与耗时
```

模型不可用或输出不可解析时回落到规则生成结论，并在结果中标注 `engine=rule-stub`，与模型结论区分开。

## 7. 通知与节奏

- **工单通道**：工单创建、根因变化、关闭、恢复时推送；同一工单每天最多一张，恢复卡不受限。
- **事件通道**：按告警粒度推送（告警创建与恢复），用于观察原始告警流。
- **每日汇总**：固定时点列出未恢复工单及其当前根因与置信度；默认只在有未恢复工单时发送。
- 未配置 webhook 时卡片写入 `data/outbox/*.jsonl`，内容与线上一致，便于离线核对。

## 8. 可观测性

- `/healthz`、`/readyz`（含各外部依赖与通道的当前状态）、`/metrics`（接收量、去重量、关联动作分布、
  分析成功率与耗时、推送计数与抑制计数、队列与巡检指标）。
- 每个工单有完整时间线：创建、告警挂入、合并、采集、分析、推送、恢复、重开。
- 归档保留原始请求，可按事件 ID 回溯校验。

## 9. 降级矩阵

| 依赖缺失 | 行为 |
| --- | --- |
| Prometheus | 富化降级为 PARTIAL，诊断在证据缺口下给出结论；恢复只依据告警源信号 |
| Kubernetes 只读 | 跳过节点/Pod 事实，实体 IP 不做纠正 |
| 模型 | 规则兜底，标注 `engine=rule-stub` |
| 飞书 webhook | 干跑落盘，指标区分干跑与真实发送 |
| 任一依赖 | 都不阻塞事件接收与工单状态推进 |

## 10. 扩展点

- **新增故障链**：在 `rules/` 下补关联规则与上下文查询模板，必要时在实体标准化里补实体类型。
- **新增告警源**：实现一个与 `NormalizedEvent` 对齐的适配层即可，下游不用改。
- **新增实体类型**：在标准化阶段确定 `entity.type`，并在恢复判据里给出该类实体的权威判据。

## 11. 已知限制与二期方向

- 单副本：SQLite 与进程内锁，不支持多实例；二期换可靠队列（数据库 outbox + 独立 worker）与共享存储。
- 关联规则目前覆盖节点与 Pod；GPU、存储、网络设备等故障链待补。
- 上下文采集是指标 + 事实 + 拓扑，尚未纳入日志与变更事件；二期待接入后可做同源比对与变更关联。
- 大模型结论仅作辅助：证据、置信度、原始输出全部留档，最终判断由人做。
