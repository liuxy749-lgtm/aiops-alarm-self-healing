**评审对象：** `design-doc/aiops-phase2.md`（v2.0-design，1818 行 / 47 章）
**评审方：** 一期实施方（同期完成一期代码与实盘联调）
**评审日期：** 2026-09-11
**评审方法：** 逐章通读 + 与一期已交付代码逐条核对（所有事实性问题均给出 `文件:行号` 证据）

## 3. 工程缺口（9 项，均已在文档中补上）

### 3.1 会丢数据的两项

**① PG 迁移的停写窗口与夜莺重试冲突（最严重）**
夜莺 Callback 媒介配置是「重试 3 次 / 间隔 3000ms」，即首次失败后约 9 秒就放弃。
§5 的迁移流程只写"停写"却没给窗口上限 —— 停写超过约 10 秒，这段告警被夜莺丢弃且不可恢复。
→ 已补入 §48.2：三种方案（先导出再停写的增量切换 / 切换期临时改指向备用接收端 / 明确接受缺口）+ 必须选告警低谷期。

**② DB 与归档文件必须同批迁移**
`raw_events` 表只存「文件路径 + 字节偏移」，正文在 `data/raw_events/*.jsonl`。
DB 挪机器而归档没挪 → 所有归档指针失效。
→ 已补入 §48.3。

### 3.2 会让验收过不了的三项

**③「飞书只能发送一次」缺硬约束**
`feishu_messages` 表无唯一约束（一期现状），`task_outbox.task_id UNIQUE` 只保证不重复入队；Worker 租约超时重投递仍会重复发。
→ 已补入 §34：`UNIQUE(incident_id, kind, dedup_key)`。

**④ `evidences` 表缺唯一约束**
根因提升触发 context v2、或人工 reanalyze 时同一份证据会反复插入。
→ 已补入 §12：`UNIQUE(incident_id, fingerprint)`，思路复用一期 `uq_incident_alert`。

**⑤ 单副本约束不会因为换 PG 自动解除**
一期 `PROCESS_LOCK` 是**进程内** `threading.RLock`。换 PG 后若直接起多副本，两个副本各持本地锁，仍会重复建工单、重复发卡片。
→ 已补入 §48.5：锁粒度收窄 + PG advisory lock（或完全依赖 SKIP LOCKED + 唯一索引）+ `/readyz` 暴露锁状态。

### 3.3 交互与延迟的两项

**⑥ §25 的卡片按钮做不了**
一期接的是**自定义机器人 Webhook**（`/open-apis/bot/v2/hook/...`）：只能发卡片，**不能接收按钮回调**。`[确认根因]/[诊断不准确]/[重新分析]` 这类按钮无法实现。
→ 已按"本期不使用自建应用"改写 §25，并新增 §49 完整交互方案：
可做 URL 按钮（跳转工单）；反馈走 API（`/feedback`、`/confirm-root-cause`）或极简页面；将来要回调需换自建应用（路径已记录在 §49.5）。

**⑦ 延迟会叠加，没有端到端预算**
一期只有单点超时（上下文 30s、LLM 60s、飞书 8s）。二期叠加"夜莺批量 + 聚合窗口 + 诊断"后，最坏可能 1 分钟以上才到群。
→ 已新增 §50：链路分解、分级预算（P0≤30s / P1≤45s / P2≤90s / P3≤150s）、组合规则（**P0/P1 不进批不进窗口**）、超时护栏（P0/P1 诊断超时先发初步卡片）、三个必需指标。

### 3.4 知识与合规的两项

**⑧ embedding 选型与维度未定就建表 = 将来全量重建**
→ 已新增 §51.1：内网优先（全文/摘要比 IP 更敏感）、维度建表前定死、失败不阻断；并提示 `knowledge_entries` 的向量列在选型确定前不要建。

**⑨ 只做关键词过滤不足以脱敏**
§29 只过滤凭据类关键词。但进向量的文本来自日志与工单，还带主机名/IP/集群名/项目名/镜像地址/任务名/目录/内网域名。
→ 已补入 §51.3：复用一期 `AIOPS_MASK_ASSETS` 的掩码函数，且**知识条目写入前与向量化前各过一次**（防止只脱敏展示、没脱敏向量）；掩码策略变更要重建向量。

### 3.5 一项建议降级

**⑩ K8s watch 第一版不要开**
watch 需处理 `410 Gone`、resync、长连接重连，且显著增加 API Server 压力。一期已是 pull 模式。
→ 已补入 §11：RBAC 可先授予，代码只用 `get/list`，用 `SYNC_K8S_TOPOLOGY` 周期同步。

## 4. 排期与依赖的现实性

文档 §41 给了 8 周排期，按**全职单人**估算，且 M2 压着两个尚未确认的前提：

``` text
未知一：日志有没有集中采集？用 Loki 还是 Elasticsearch？（§42 第 3 条自己也在问）
未知二：变更事件源有哪些？（K8s rollout / Ansible / CI-CD / 人工）
```

这两件不确认，Week 5–8 排不准。建议分档：

| 档 | 内容 | 可排期性 |
| --- | --- | --- |
| M0（可立即开始） | Prometheus 查询 API、K8s 只读、模型、夜莺 Pod node 标签 | 1 周内可完成，无架构风险，立刻产生价值 |
| M1（先出 PG 落地清单 + 迁移演练再定日子） | PG、Outbox、Worker、聚合窗口 | 牵扯数据迁移与锁改造，最容易出事 |
| M2（先做半天前置调研） | 日志、变更、Evidence、Postmortem、Knowledge、RAG | 依赖外部平台现状 |

## 5. 已确认的决定

| 事项 | 决定 | 影响 |
| --- | --- | --- |
| Prometheus 接入方式 | 接**查询 API**（`/api/v1/query`、`/api/v1/query_range`），**不接 Alertmanager 告警** | 告警已由夜莺负责；Prometheus 只提供指标证据。已在 §10 写明 |

| 飞书交互 | **本期不使用自建应用**，不做卡片按钮回调 | §25 已改写，§49 给出替代方案；未来升级路径已记录 |
