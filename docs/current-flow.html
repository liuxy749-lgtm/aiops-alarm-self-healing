半夜机器生病了，谁来看病？

这份网页用最简单的话，讲清我们这套「告警自动处理系统」现在是怎么运转的。

不用懂技术也能看懂：把每个部件想成一个人，看看他们怎么接力。

当前版本：一期 + 副作用出锁（2026-09-11） 入库只要约 100 毫秒 AI 看病要 5~16 秒

一、先认识这几个人

夜莺（值班保安） 一直在盯着机器。哪台机器不对劲，它第一个发现，然后马上打电话通知别人。
真实名字：Nightingale 监控告警系统
网关（接线员） 接到电话第一件事：先在记事本上写下来，然后立刻说“收到！”，绝不让对方一直等着。
真实名字：aiops-gateway（我们自己的程序）
记事本（档案柜） 所有来电原文都一字不改地留着，以后复查、学习都靠它。
真实名字：raw_events 文件 + SQLite 数据库
侦探（关联警察） 接到很多电话时会想：这些是不是同一件事？同一台机器、时间又接近，就是同一场病，合成一张单子。
真实名字：Correlation Engine 关联引擎
取证员（跑现场） 去看机器最近的“体温曲线”，再翻翻机器的台账（哪些程序在跑、状态正不正常）。
真实名字：Prometheus 指标 + K8s 只读接口
‍
医生（AI） 拿着证据判断“最可能是什么病”，并且必须说清：证据是哪几条、有几成把握。
真实名字：DeepSeek 大模型
大喇叭（群里喊人） 把结论贴到工作群里，让该处理的人一眼看懂发生了什么。
真实名字：飞书群机器人
‍
助手（后台慢工） 接线员说完“收到”就把活儿交给助手：跑现场、请医生、发通知，都由助手慢慢做。
真实名字：后台 worker（副作用出锁）

二、然后，事情按 8 步发生

第 1 步：保安发现机器不对劲，打来电话

比如一台机器的“心跳”不见了（专业说法：节点 NotReady）。保安立刻给接线员打电话。

真实动作：夜莺用 HTTP POST 把告警发到 192.0.2.115:8701/api/v1/events/nightingale

第 2 步：接线员第一件事——把电话内容一字不改地记下来

就像接到重要电话时，先记在纸上，免得等下忘了细节。记完才做别的。

真实动作：原始告警原封不动写进按天切分的 JSONL 文件（data/raw_events/），并记下文件位置

第 3 步：看懂它在说什么

电话里可能说得很乱。接线员把它整理成一句人话：哪台机器、什么毛病、多严重、什么时候发生。

真实动作：标准化（Normalize）→ 实体 + 严重级 + 发生时间 + 幂等键

第 4 步：同样的话说两遍，只算一次

这样做的原因：保安有时会重复打同一个电话（网络重试、告警反复触发）。如果每次都当真，群里就会被同一条消息刷屏。所以每通电话都有一个“指纹”，一样的指纹只处理一次。

真实动作：幂等键 = 夜莺 hash + 状态 + 触发时间；数据库还有唯一约束兜底，绝不重复建单

第 5 步：侦探判断“这是不是同一件事”，合成一张工单

一起来的十通电话，可能是同一场病。侦探按这几条线索打分：同一台机器、机器之间有从属关系、同一个集群、时间很接近。分数够了就合成一张工单。

真实动作：关联打分（同节点 +40 / 拓扑 +30 / 同集群 +10 / 1 分钟内 +20，阈值 70）→ 生成或挂入工单，并标出谁是根因、谁是症状

第 6 步：接线员立刻说“收到！”（约 100 毫秒）

到这一步，接线员已经记录完了，他就马上回一句“收到”，然后腾出手去接下一个电话。注意：他还没去看现场、还没请医生。

真实动作：返回 HTTP 200， 87~124 毫秒（以前要 11~15 秒）

第 7 步：助手慢慢干活——跑现场取证

助手先去看机器最近的“体温曲线”（CPU、内存、网络丢包、磁盘忙不忙……），再去翻台账：机器在集群里是什么状态、上面跑着哪些程序、有没有异常记录。

真实动作：Prometheus 查历史曲线（一次 4~14 条查询）+ K8s 只读接口读节点状态/Pod 列表/事件

第 8 步：医生看证据下判断，然后群里喊人

医生必须做到三件事：① 说最可能的原因；② 把用到的证据一条条列出来；③ 说有几成把握。证据不够就必须承认“看不准”，不许瞎猜。

真实动作：DeepSeek 生成「结论 + 证据 + 置信度 + 建议排查步骤」→ 飞书卡片推到群里（创建 / 根因变化 / 关闭 三个时机各推一次，不刷屏）

四、第 6 步为何“先说收到、再慢慢干活”？

以前的做法（会出问题）

接线员接到电话后，一直拿着话筒不吭声：先跑现场、再请医生、再把结论写好，整整 11~15 秒才说“收到”。

打电话的保安等不及了，心想「是不是没人接？」，于是挂掉重打，打不通又重打……结果同一起故障被当成新故障，建了好几张单子、群里刷了好几遍。

真实现象：夜莺报 context deadline exceeded (Client.Timeout exceeded while awaiting headers)，但群里其实收到了卡片 —— 因为我们的活儿干完了，只是回话太慢。

现在的做法

接线员先说“收到”（约 100 毫秒），再把活儿交给助手，自己去接下一个电话。等医生看完病，结果再单独通知。

好处：保安不再重复打电话；就算同时来一百个电话，也不会一个卡住全部（以前第一次超时会把后面所有告警都堵住）。

给好奇的大人：这一改动在程序里是怎么做的？
  • 网络请求里只做“数据库短事务”：存原文 → 整理 → 提高等级/去重 → 建工单，全部是毫秒级动作。
  • “取证 + AI + 通知”被放进后台单线程队列（app/services/worker.py），不再占用那个网络请求。
  • 工单上记了进度：PENDING（排队中）→ RUNNING（正在做）→ DONE（做完了）/ FAILED（失败了，附原因）。运维一眼就能看出“工单为什么还没有诊断”。
  • 如果程序被重启，第 2 步记录的进度会告诉它「哪些活儿还没干完」，启动后自动接着干。
  • 留了一个总开关 AIOPS_INLINE_ANALYSIS=true：万一新做法有问题，改一行就能退回“老办法”。

六、现在的成绩单

⏱ 速度

  • 入库（说“收到”）：约 100 毫秒（以前 11~15 秒）
  • AI 看病：5~16 秒
  • 群里看到卡片：约 10~15 秒后

靠谱程度

  • 42 个自动化测试全绿
  • 同一告警重复送 100 次 → 仍然只有 1 张单子
  • 8 条告警的风暴 → 合成 1 张工单（压缩率 87.5%）

安全边界

  • 只许看集群，不许改（连读密码都不给）
  • 资产名字在出网前先换成代号，回来再换回真名
  • 它不会登录任何机器、也不会执行任何命令

记性

  • 原始告警留 30 天，工单/事件留 90 天
  • 每次诊断的“证据 + 置信度”都存库，可复查

七、老实说，现在还做不到这些

  • 它不能自己修：只诊断、只通知，动手还得人来（这是有意的）。
  • 它不能登录机器：所以给的建议里会写“请人工执行 ethtool / dmesg”这类需要人做的事。
  • 它还看不到日志内容（二期要加：从 K8s 接口拉容器日志当证据）。
  • 它不知道“刚改过什么”（二期要接变更记录：故障前有没有人发版、改配置）。
  • 它没有历史记忆：还不能说“这毛病上个月出现过，当时是这么解决的”（二期做知识库）。
  • 它还只有一台：这台机器挂了就全停（二期换数据库 + 多副本）。
  • 第一张卡片可能只显示 1 条告警：因为它发得太快了（二期加“等 30 秒再发”的聚合窗口）。

八、小词典（术语 → 小朋友说法）

术语说人话
告警（Alert）“这台机器不对劲”的一条通知
工单（Incident）把同一场病的多条通知合成的一张病历单
根因 / 症状病根（机器坏了） / 表现（上面跑的程序也不正常了）
富化（Enrich）给这条通知补上背景资料：机器在哪、什么配置、谁家的
上下文（Context）医生看病前收集的全部证据（曲线 + 台账）
置信度（Confidence）医生说的“我有几成把握”
幂等同一句话听一百遍也只当一遍
